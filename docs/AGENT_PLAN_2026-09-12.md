# 往 agent 上靠 · 规划（2026-09-12）

> 用户：「能够怎么样往 agent 上靠吗，我想做一做」。
> 这份文档只做规划与路线选择，**没写实现代码**。相关现状见 `docs/HANDOFF_2026-09-12.md`。

---

## 0. 先对齐"agent"指什么

roleworld 现在是**单轮生成**：拼一段 system 提示 → 模型回一段话 → 前端解析标记（`[[记住: …]]`、
`[[事件: …]]`、`[[搜索: …]]`）→ 写记忆/检索 → 结束。

"往 agent 上靠"在我们这个产品里有三种意思，成本与风险完全不同：

| | 是什么 | 用户能感知到的差别 |
|---|---|---|
| **A. 角色会用工具** | 模型自己决定"先查一下记忆/查一下世界书/记下来"，多步循环后再开口 | 角色**真的记得住、查得到**，而不是靠提示词叮嘱；回复里能看到"（查了记忆：…）" |
| **B. 导演 agent**（剧情模式） | 一个独立的调度者维护"故事现在到哪了"，决定下一个谁说话、要不要推进剧情 | 多角色场景不再是"轮流硬编"，剧情会自己往前走 |
| **C. 后台主动 agent** | 角色主动找你说话 | **用户明确说过不要，不做**（写在这里免得以后有人乱加） |

**建议先做 A**：它是地基。而且我们现在已经有三个"伪工具"（`[[记住]]`/`[[事件]]`/`[[搜索]]`，
本质是让模型吐标记、前端正则解析），升级成真正的工具调用是**同一件事的下一步**，不是换方向。

## 1. A 路线怎么做（角色工具箱）

### 1.1 工具清单（第一批只上 4 个，宁少勿多）

| 工具 | 参数 | 干什么 | 现在靠什么凑 |
|---|---|---|---|
| `search_history` | `query`, `limit?` | 在旧对话里检索原话并给出处 | `[[搜索: …]]` 标记 + 前端检索 |
| `remember_fact` | `text` | 记一条关于玩家的事实（长期） | `[[记住: …]]` |
| `remember_event` | `text` | 记"你们之间发生过什么"（注入时带 `[此前发生]`） | `[[事件: …]]` |
| `lookup_lore` | `topic` | 查这个角色的世界书 / 原著剧情书 | 现在是关键词自动命中（不可控） |

第二批候选（等第一批稳了再说）：`advance_time`（推进故事内时间，伴侣模式的时间感就有真实来源）、
`change_scene`、`roll_dice`（剧情模式已有骰子，可以变成工具）、`introduce_character`。

### 1.2 执行链路（关键设计）

```
用户这句话
   ↓
composeMessages(带 tools)
   ↓  ① 请求模型
模型返回 tool_calls ──→ 本地执行（只读/只写本机数据，不出网）
   ↑                        ↓
   └── 把工具结果塞回 messages（role: "tool"）
   ↓  ② 再请求一次（最多 N 步）
最终文本回复 → 落盘
```

- **预算硬上限**：每轮最多 `2` 次工具调用、最多 `3` 次模型请求（超了就强制它用现有信息回答）。
  没有上限的 agent 循环 = 烧钱。
- **工具只在本机执行**：检索旧对话、读写记忆、查世界书全在本地，不额外发数据出去。
- **可回放**：每次工具调用记进台账（`metrics`），「本次请求」面板里能看到"这一轮调了什么"。
- **UI**：回复上方一条灰色小行「（查了记忆：关于团子）」，让用户看得见角色做了什么 —— 这本身就是"agent 感"。

### 1.3 成本（必须让用户知道）

- 一轮里多一次模型请求 → **token 与时间都翻倍**；体验卡按**请求次数**计费，
  所以同学的卡会烧得更快。两条应对：
  1. 工具循环只在"模型真的要求用工具"时才发生（大多数普通寒暄 0 次）；
  2. 体验卡的卡面说明与开场里写明"带工具的一轮可能算 2 次"，并把每轮上限摆在设置里。
- 需要一个设置开关：「让角色自己查资料 / 记东西（默认开）」+ 「每轮最多几次」。

### 1.4 测试（这套必须能离线测）

- `adapter-unit`：工具定义（JSON Schema 合法）、`tool_calls` 解析、预算上限（第 3 次不再执行）、
  工具结果回灌的消息形状、失败工具（检索为空）不炸。
- `local-app-check`：假模型端点第一次返回 `tool_calls`、第二次返回正文 → 断言
  ① 界面出现工具行 ② 记忆真的写进去了 ③ 「本次请求」面板里能看到这一步 ④ 台账记了两次请求。
- 新增一套 `tests/agent-check.cjs`（第 12 个套件）：多步、上限、工具报错、混合场景。

## 2. B 路线（导演 agent，剧情模式的自然延伸）

A 做完之后，B 几乎是顺水推舟：**导演 = 一个只有工具、不演角色的调度者**。

- 维护一份**故事状态**（KV 存、可查看可改）：在场角色 / 地点 / 故事内时间 / 未解伏笔 / 上一轮谁说过话。
- 每回合先让导演输出一个 JSON 计划（谁说话、要不要插入事件、要不要推进时间），角色照着演。
- 用户能当"上帝"改这份状态 —— 与现在「我在场」开关、导演模式是一套。

成本：每回合 +1 次请求（可用"每 N 回合调度一次"来省）。

---

## 3. 不做 / 要慎重的

- **主动消息**：用户明确不要（`docs/COMPANION_MODE_PLAN_2026-09-11.md` 与 0.1.x 的硬规矩）。
- **让 agent 自己动用户的文件 / 发网络请求**：不做。工具白名单只碰"对话、记忆、世界书"这三样。
- **无限循环 / 自我反思多轮**：不做，必须有硬上限。

## 4. 建议的推进顺序

| 步骤 | 内容 | 估计 |
|---|---|---|
| 1 | `app/agent-tools.js`：4 个工具的定义 + 本地执行器（纯逻辑，可单测） | 2–3 小时 |
| 2 | `task22-core.js`：`tools` 进请求体、`tool_calls` 解析、消息回灌 | 2 小时 |
| 3 | `integration.js`：`runToolLoop`（带上限）+ 工具行 UI + 设置开关 | 3 小时 |
| 4 | 设置里两行（开关 + 每轮上限）+ 体验卡说明补一句"带工具的一轮可能算 2 次" | 1 小时 |
| 5 | 三套测试（adapter / local-app / 新 agent-check）+ 全量回归 | 3 小时 |
| 6 | 上线（要重出桌面包） | — |

**合计约一天半**，做完就是 0.2.0 级别的变化（产品从"会聊天"变成"会自己做事"）。
